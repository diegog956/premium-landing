# Creative orchestration and anti-slop gate

## Authority order

Do not average specialist opinions. Resolve conflicts in this order:

1. verified business facts, approved brand kit, rights, and hard constraints;
2. approved visual contract and selected references;
3. `frontend-design` as visual director;
4. `design-taste-frontend` v2 as contextual anti-slop challenger;
5. `ui-ux-pro-max` as consultative evidence only;
6. Emil skills as motion specialists only;
7. technical and screenshot auditors as release gates.

No specialist may silently replace the chosen reference grammar, stack, brand typography, or content strategy with its own defaults. More skills do not create more authority.

## Preflight artifact

Before coding, add a concise creative preflight to `.premium-landing/brief.md`:

- one-line design read covering page kind, audience, visual language, and reference family;
- three or more project-specific visual decisions traceable to the brief, brand assets, content, or selected reference;
- the intended composition, typography behavior, imagery treatment, density, and motion purpose;
- at least three plausible AI defaults explicitly rejected for this project and why;
- any deliberate use of a commonly abused device, with the project-specific reason it belongs.

Do not satisfy this by naming styles. Each decision must constrain the actual implementation.

## Taste v2 role

Use `design-taste-frontend` to challenge defaults, incomplete execution, generic visible copy, repetitive page anatomy, and mechanical layout patterns. Apply its rules contextually. Ignore any rule that conflicts with verified brand assets, the approved visual contract, accessibility, the established stack, or a stronger observed reference property. Do not import its React, Next.js, Tailwind, font, icon, dark-mode, or motion defaults into an Astro project unless independently justified.

Do not stack `design-taste-frontend` with another Taste variant in the same run. Do not use `high-end-visual-design` as a general gate: recipe-driven premium styling can itself create recognizable slop.

## Blocking anti-slop proof gate

Inspect the rendered desktop and mobile proof plus the implementation. Fail the proof when any of these is true:

- its structure could be transferred to an unrelated business by changing only text, colors, and images;
- fewer than three material visual decisions can be traced to project evidence;
- the page defaults to a centered hero, generic bento/features grid, interchangeable cards, pills, glows, glass, mixed-serif emphasis, or stock SaaS composition without explicit justification;
- typography, crop, spacing, or motion contradicts the selected reference while the agent claims fidelity;
- distinctiveness exists only in decoration rather than composition, hierarchy, content, imagery, or interaction;
- the agent explains why the design is premium instead of demonstrating it in screenshots;
- Taste rules are followed mechanically at the expense of the approved direction.

Record the failed cause, revise the proof, and rerun the gate. Do not expose a known generic proof for operator approval.

## Motion workflow

Build the static proof first. Then:

1. Run `find-animation-opportunities`; keep its accepted and rejected candidate evidence.
2. Select only motion with a named purpose: feedback, spatial consistency, state indication, explanation, or prevention of a jarring change.
3. Implement with `emil-design-eng`, extending the project's existing motion tokens and choosing the lightest suitable technology.
4. Run `review-animations` against rendered behavior on desktop, touch behavior when relevant, and `prefers-reduced-motion`.
5. Use `improve-animations` only when failures are systemic enough to merit a remediation plan.

Motion cannot rescue a generic static composition. Delete motion that exists only to signal expense or novelty.
